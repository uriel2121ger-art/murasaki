**Particle system record (WE 2.8.42).** The top level reads
`material` (string), `starttime` (number, default 0), `animationmode`, `sequencemultiplier` (number, default 1), `flags`
(an integer) and `maxcount` (default 0), then `emitter`, `initializer`, `operator`, `renderer`, `controlpoint` and `children`.
`animationmode` has two values only: "randomframe" is the random-frame mode, any other word (including "sequence", "once" or
none) plays the sequence; the engine follows that ("once" loops here too). Random frame also
sets flag bit 1 (no frame blending); this engine never blends sheet frames, so bit 1 holds for every system. Flag bit 2
(perspective) sets an internal render value of its own. The names of the file's bits (`worldspace`, `disable_*_override`) are not
in the renderer: the file's bits are tested by number. Bits from 0x10000 up are WE's own, derived from the members (renderer
`uvsmoothing`, `uvscrolling`, `minlength`, a `hascolor` member, a low quality setting), and never come from a file.

## What this means for M3, in order

1. **Everything a typical item needs**: emitters `sphererandom` (36 items) and `boxrandom` (19); initializers `lifetimerandom`, `sizerandom`, `colorrandom`, `velocityrandom`, `alpharandom`, `turbulentvelocityrandom`, `rotationrandom`, `angularvelocityrandom`; operators `movement` (gravity, drag), `alphafade`, `sizechange`, `oscillatealpha`, `angularmovement`; renderer `sprite` (41 of 44 items). Nearly all systems use the same few types, so the data model covers them in one pass.
2. **Next by frequency**: operators `turbulence` (19 items), `controlpointattract` (10), `oscillateposition` (10), `colorchange` (9), `oscillatesize` (4); renderers `spritetrail` (20 items) and `rope` (6); `ropetrail` (3).
3. **Children** are in 23 items (`eventfollow` in 5, the rest untyped = static children that follow the parent), so parenting is needed early.
4. **Control points**: 43 of 44 items have them, almost all with flags 0 (a fixed point); flags 1 (14 items) and 2 (1 item) follow the pointer or another object. The pointer-linked ones use the corrected pointer convention.
5. **Instance overrides** in `scene.json` (`size`, `colorn`, `count`, `alpha`, `rate`, `speed`, `lifetime`, `color`) are used by up to 20 items: they are part of the data model, not an extra.
6. **Later or never**: `mapsequencearoundcontrolpoint` and `mapsequencebetweencontrolpoints` (one item, rejected with a reason), the audio-reactive emitter members (done, see the last section), `sprite` `orientation`/`axis` variants (done).
7. Materials are WE's `presets/*.json` and `particle/*.json`; they go through the M2 translator (`genericparticle` and the rope/trail variants), so `--check` names a compile failure like any other shader.

## How it is built (M3)

Everything above is implemented except what the last section of this file lists as later. The code is in `src/scene-vk/particles/` (data and simulation, no GPU) and `src/scene-vk/render/particlerenderer.*` (vertices and draws).

**Space.** Particle files use scene axes (x right, y up): `gravity` `0 -300 0` pulls down, `origin`, `directions` and velocities need no flip. A system lives in its object's space (origin, angles, scale, parents and camera parallax of the object apply; the object's `parallaxDepth` is used as written, default 0). Control points are in that space; those with flag 1 follow the pointer (the pointer in scene units through the inverse of the object's matrix, plus the offset), flag 2 means the offset is in scene space.

**Simulation.** Fixed steps of 1/60 s, at most 0.1 s caught up per frame (a stalled process does not simulate minutes). `starttime` is simulated at start in steps of 1/30 s (up to 120 s) so embers and snow begin populated. Emitters: `boxrandom`, `sphererandom` (a ring in x/y, or a shell with flag 4), with rate, delay, duration, `instantaneous`, burst flags, `sign`, own speed, and the object's `rate` and `count` overrides. Initializers: lifetime, size (the file's number is twice the drawn width), colour (0..255 or 0..1), alpha, velocity, rotation, angular velocity, turbulent velocity (own curl noise), map sequence around and between control points. Operators: movement (gravity, drag), angular movement, alpha fade, alpha/size/colour change, turbulence, control point attract, oscillate alpha, size and position. The instance override (`alpha`, `size`, `lifetime`, `rate`, `speed`, `count`, `colorn` or `color`, `controlpointN`) multiplies on top and may be bound to user properties; a change rebuilds the system. `MURASAKI_SCENE_VK_SEED` makes a run reproducible.

**Drawing.** One indexed draw per system into the scene target, in file order with the image layers, with the material's blending. The vertex layout is WE's own (`a_Position`, `a_TexCoordVec4` = uv, rotation z, size; `a_Color`; `a_TexCoordVec4C1` = velocity and lifetime or sprite frame; `a_TexCoordC2` = rotation x, y), so `genericparticle` is translated and used unchanged, with the combos `THICKFORMAT`, `SPRITESHEET` (a texture with frames; `g_RenderVar1` carries the grid), `TRAILRENDERER` (`spritetrail`, `g_RenderVar0` the trail lengths) and the `TEX<n>FORMAT` ones the engine adds for every bound texture (R8 and RG88 samples are rebuilt by the shader, compressed normal maps decoded by it). REFRACT materials read a snapshot of the scene drawn so far. Ropes (`rope`, `ropetrail`) use `genericropeparticle` with a 26 float vertex: the rope is a Catmull-Rom ribbon through the particles in spawn order; a rope trail keeps a history of `segments` states per particle (one every `length / segments` seconds) and draws one ribbon per particle.

**Children.** `static` children are systems of their own placed by the child's origin, angles and scale. `eventfollow` children are one copy per live particle of the parent (the newest `maxcount`), each with its control point 0 on that particle; a copy whose particle died stops emitting and goes when its own particles do. `eventspawn` and `eventdeath` are refused (none in the library).

**Perspective particles** (flag 4: the snow and rain presets) are drawn through a camera 1000 units in front of the middle of the scene with the scene's `fov` (50 by default): particles with z towards the camera are larger. ASSUMED: the vertical field of view; WE's own numbers are not documented.

**Cost.** A scene with a particle system redraws every frame; a paused engine renders nothing, and a system whose object is hidden neither simulates nor draws. Vertex buffers are host-visible and grow by doubling with the largest live count.

## What is refused (M3)

`--check` names the first thing it cannot do: `particles: emitter|initializer|operator|renderer <name>`, `particles: child <type>`, `particles: material ... cannot be read`, `particles: an object with an inline definition`, and `SceneScript (particle ...)` for scripted values (M4). With the library of this machine every particle item is accepted except those with scripts or audio-reactive emitters (M4).


## Limits (hostile and accidental input)

- **Systems per object:** at most 256 (the object's own system plus every system its children expand to; `ParticleDefinition::systemCount`). A file listed many times as a child is parsed once per depth, so a fan-out of 10x10x10 costs a few file reads; more than the limit makes `--check` refuse the item (`particles: more than 256 systems in one object`). A `eventfollow` child that has an `eventfollow` child of its own is refused too (`particles: nested eventfollow`).
- **Followers:** an `eventfollow` child keeps at most 256 copies (its `maxcount`, clamped), found in one pass with a hash map.
- **Numbers:** values from user properties and files are finite and within 1e9 (`ParticleComponent::number`/`vector`/`integer`); the instance overrides are finite, 0 to 10000 (`sanitizeOverrides`); ranges given to the generator are finite and bounded; rates and burst counts are clamped before the float-to-integer casts. A particle with a non-finite position, colour, alpha or rotation is not drawn.
- **Simulation work:** `warmUp` stops after 5 million particle-steps; an emitter's `delay`, `duration` and burst clocks keep running while the pool is full.
- **Memory:** a rope trail's history is cut to 2 million states per system (64 MB; a pool of 150000 gets 13 points, not 64). Vertex buffers are limited to 128 MiB per system and 256 MiB over all systems, and to 500000 quads; sprites are cut to what fits, a rope or trail that does not fit is left out, and the first time is logged. A failed buffer allocation skips the system (logged once) instead of ending the process. The shared index buffer that is replaced while a frame is recorded is kept until the next frame starts.
- **Rebuilds:** a `count` override that changes (a slider) rebuilds the object at most four times a second, with no device wait.

## Added for the reference library

- **`vortex` operator**: around the axis (`axis`, default z) through control point `controlpoint` (plus `offset`), inside `distanceouter` a particle's velocity gets a push along the circle (axis x radial, counter-clockwise from the axis' tip) of `speedinner` units/s near the axis to `speedouter` at the outer distance. Its `audioprocessing*` response follows the spectrum (see the audio section); `flags` are not read (reported as degraded).
- **`boids` operator** (assumption: nothing documents it; 3815761795, 3820467076 and 3812518176 use `neighborthreshold`, `cohesionfactor`, `alignmentfactor` and `separationfactor`): every particle steers by the others closer than `neighborthreshold` (default 100): towards their centre at `cohesionfactor` per second of the distance to it, towards their mean velocity at `alignmentfactor` per second of the difference, and away from those closer than `separationthreshold` (default half the neighbour distance) at `separationfactor` times the neighbour distance per second, more the closer they are. `maxspeed` caps the speed when given. Flat systems flock in x and y. Neighbours come from a grid of cells the neighbour distance wide, at most 48 a particle, so the cost stays linear. `flags` is not read.
- **`hsvcolorrandom` initializer**: a colour drawn in HSV, `huemin`..`huemax` (0..1, wrapping; default 0..1), `saturationmin`..`saturationmax` and `valuemin`..`valuemax` (default 1..1), times the instance colour, like `colorrandom`.
- **`remapvalue` operator** (assumption: nothing documents it; the library's rain presets are the only users): `output` `velocity` sets the velocity to a point of `outputrangemin`..`outputrangemax` (vectors) and `speed` sets its length to a point of a scalar range, keeping the direction. The point comes from a value noise of the particle's position (`transforminputscale` cells per 1000 units; `fbmnoise` adds two finer octaves, every other `transformfunction` is plain noise), each velocity component with a noise of its own. `operation`, `flags` and the other outputs (size, alpha, colour...) are not read: those outputs leave the particle alone.
- **Event children**: `eventspawn` and `eventdeath` children make a copy of the child where a parent particle is born or dies (its control point 0 there). The copy emits once (the child's instantaneous burst; its continuous rate is not run) and lives until its particles are gone. At most the child's `maxcount` copies (256 at the most) live at a time and 16 are made a frame.

## Audio-reactive emitters and renderer orientation

The parts below marked **assumed** are not established by the files.

- **Emitter audio response** (`audioprocessing*`, 38 library scenes). `audioprocessingmode` (default 0 = off), `audioprocessingexponent` (2.0), `audioprocessingbounds` ("0.8 1.0"), `audioprocessingfrequencystart` (0) and `audioprocessingfrequencyend` (1); both frequencies are clamped to 15 (they index the 16-band spectrum) and swapped when the end is below the start. **Assumed:** mode 1 is the left channel, 2 the right, 3 both (their mean); the level is the mean of the bands start..end (inclusive) of that channel, 0..1; the response is `boundsMin + (boundsMax - boundsMin) * pow(level, exponent)`; it multiplies the emitter's emission rate (`rate` times the instance's rate override) and nothing else: `instantaneous` bursts, speed, size and alpha are untouched. A negative mode is off; a mode above 3 is read as 3 and reported as degraded (`particle emitter audio mode N`); an `audioprocessingmode` on a `vortex` or `turbulence` operator is followed (next paragraph), on any other operator it is not and is reported as degraded (`particle operator audio response`). With no audio (silence, no capture, the snapshot tool) the rate is the bounds' minimum, 0.8 by default.
  The spectrum is the engine's own (`g_AudioSpectrum16Left/Right`, audio/spectrum.h); `ParticleRenderer::update` hands the 16 bands of both channels to the systems of the visible layers each frame (hidden layers stand still, and followers or event copies made during a frame get silence until the next one), and a scene with such an emitter makes the engine capture audio (`ParticleRenderer::usesAudio`).
- **Renderer orientation** (`orientation`, `axis`; about 25 library scenes). `orientation` "upright" is mode 1, "fixed" mode 2, anything else (including "screen" and no member) mode 0 and draws as before; another word is reported as degraded (`particle renderer orientation X`). The pass gets the combo `ORIENTATION` = mode when the mode is not 0 (only the rope shader's geometry stage reads it; the engine builds ribbons on the CPU and its vertex stage uses `g_OrientationForward` as the eye direction, so the combo is carried for completeness). `axis` is "x y z"; all zero or absent means (0, 1, 0) (WE's own default, read from its renderer reader, below), else it is normalised: A. B = normalize(cross((0, 1, 0), A)), or (1, 0, 0) when A runs along y; C = cross(A, B). The shaders build each sprite's basis as `rotation * mat3(g_OrientationRight, g_OrientationUp, g_OrientationForward)` (rows), so the sprite's right and up edges are `g_OrientationRight` and `g_OrientationUp` and its face looks along `g_OrientationForward`.
  **Chosen mapping (not documented by WE; same for upright and fixed):** Right = B, Up = C, Forward = A. The axis is the direction the sprite faces; WE's default A = (0, 1, 0) makes a sprite with no axis lie flat in the xz plane, edge-on to a flat (orthographic) scene. The basis is right handed (Right x Up = Forward). Axis 0 0 1 is the identity (the sprite faces the 2D view); axis 0 1 0 gives a sprite lying in the xz plane; 1 1 1 a sprite tilted to face the diagonal. How "upright" and "fixed" differ (the first perhaps keeping the up edge vertical while the second takes the axis literally) is unknown; both use the same basis here. One system is drawn by one pass, so it has one orientation, that of the first renderer that asks for one; renderers that disagree are reported as degraded (`particle renderers with different orientations`). Screen mode ignores the axis (4 items have an axis "0 45 0" without an orientation).
  **Why Forward = A with the default (0, 1, 0) (decided 2026-10-21 from the library; an assumption).** Two groups of renderers with `upright` or `fixed`: **explicit axis "0 0 1"**, 7 renderers in 6 items (2935848508, 2998757800, 3222648892, 3465215190, 3812518176 with the rain pack's `Rain_Splash_copy2` and `Rain_Splash_Drops_copy1`, and 2244339517's `Triangle_copy1`); the five rain scenes are **orthographic** (`general.orthogonalprojection`, camera along -z), so their splashes are only visible if "0 0 1" makes the sprite face the camera: that is Forward = A, with A = (0, 0, 1) the identity. Under the other reading (Up = A) the same axis would lay the sprites in the xz plane, edge-on, in five scenes whose authors made those copies to be seen, and a splash pack would have no reason to set 0 0 1 at all. **No axis**, 2 renderers (`binary_zero` in 2618988115, an orthographic scene; `towerlights_copy1` in the perspective scene 2244339517): with WE's default A = (0, 1, 0) and Forward = A they lie flat on the xz plane, which in 2244339517's perspective camera is a ground light and in 2618988115's flat scene is edge-on. What decides nothing: snapshots with each reading (seed 7, 8 s) differ by clock text and a handful of particles in the 7 items, and the previews are too small to show them; SSIM against the previews moves by less than 0.001. The readings tried were: default (0, 0, 1) with Forward = A (before), default (0, 1, 0) with Forward = A (now), and (0, 1, 0) and (0, 0, 1) with Up = A. What would settle it: the uniform upload site (ids 0x1d..0x1f) in wallpaper64.exe, which of A, B, C feeds which constant.
  **Renderer record (WE 2.8.42).** Members are `orientation` (string, default "screen"), `axis` (string, default "0 0 0") and `flags` (default integer 0, kept as one byte). Mode: "upright" 1, "fixed" 2, anything else 0 (matches the above). `axis` is parsed as three space-separated floats; **when all three are zero (also when the member is absent) WE stores A = (0, 1, 0), not (0, 0, 1)**, otherwise A = normalize(axis). Then B = normalize(cross((0, 1, 0), A)) and C = normalize(cross(A, B)); when A.x = A.z = 0 WE stores B = (1, 0, 0) and C = (0, 0, -1). The shader constants are `g_OrientationForward`, `g_OrientationRight` and `g_OrientationUp`; which of A, B, C feeds which is not established.
  **Open (smaller):** which of A, B, C WE feeds to each of `g_OrientationForward`, `g_OrientationRight` and `g_OrientationUp` is not established; the reading above is the one that makes the rain scenes' explicit "0 0 1" mean something.
  Renderer `flags` (a byte; see below for what the library shows) is not read: its meaning is unknown, and a non-zero value is reported once per scene as degraded (`particle renderer flags`).
  **Renderer `flags`, evidence (library survey, 2026-10-21, 2432 renderers of the scenes' particle files).** The member is present on 74: value 1 on 61 (53 sprites, 4 ropes, 4 rope trails; 23 items) and 0 on 13 (11 `spritetrail` of `ember_small`, 2 sprites of `leaves5`). None of the 279 renderers of WE's own presets (`assets/**`) carries it: it appears only in files the editor saved for a user. It does not follow the blending (55 additive, 6 translucent), the material (`genericparticle` always; `REFRACT` 0 or 1 in the same shares as for the other systems), the orientation (set or not), the renderer type or any member of the system (no top-level key differs by more than a quarter between the systems that have it and the other 1253); the same preset appears with and without it in different items (`fog1`, `lightning1`, `trail_1`, `vapor0`, `shootingstar`), and the only difference in the renderer is the presence of `flags` (and `orientation`). The editor has no label for it (`ui_en-us.json`). So the library does not say what bit 0 does; nothing is guessed. The byte is not read by the material or combo set-up, so `flags` changes neither the shader nor the combos nor the material; if it does anything it is in the geometry or the per-frame draw (order, subdivision, orientation or culling). A script on a renderer member is refused like those of emitters and operators.

### What is implemented, and what is assumed

Everything below is in `particles/system.cpp`; each element's comment there says the same. **ASSUMED** marks a meaning chosen from the
names, the editor's labels and the presets' values, not stated anywhere.

- **Blend window** (`blendinstart`, `blendinend`, `blendoutstart`, `blendoutend`; on `capvelocity`, `remapvalue`, `turbulence`,
  `oscillateposition` in the presets). ASSUMED: lifetime fractions; an operator's effect ramps from 0 to 1 between the two "in" values
  and back to 0 between the two "out" values (equal values: a step). Absent members: no ramp. Read by every operator added here and by
  `turbulence`, `vortex`, `controlpointattract`, `oscillateposition`, and by `oscillatealpha` / `oscillatesize` (7 library items set it
  on `oscillatealpha`), whose oscillation then fades in and out around the base value. On any other operator (movement, angular
  movement, the fades and changes, boids, the collisions, `inheritvaluefromevent`) a blend window is not read and is reported
  (`particle operator blend window <name>`): the operator works over the whole lifetime.
- **Children `probability`** (library: `eventfollow` 0.5 in 8 items, `eventdeath` 0 in 2 and 1 in many; `static` 1). ASSUMED: the chance
  that a parent particle gets a copy of an event child, drawn once per particle (a hash of its birth number and the child), so a
  follower does not come and go; 0 makes none. Static children ignore it.
- **Collisions** (`collisionplane`, `collisionsphere`, `collisionbox`, `collisionquad`, `collisionbounds`). `collisionbehavior`: `bounce`
  (default, ASSUMED) reverses the velocity across the surface times `bouncefactor` (default 1, ASSUMED), `slide` removes it, `stop` removes
  all velocity and spin ("Stop rotation on collision" is not read as a separate switch), `delete` ends the particle; any other word bounces
  and is reported (`particle collision behavior X`). Members of the collision operators other than those named here (for instance
  the editor's "Collision mask") are not read and not reported. ASSUMED: the particle's centre collides (its size is not added), and a particle
  collides only when it went through the surface during the step (it was on the free side a step ago by its velocity): one that starts
  behind a surface is left alone. Shapes are relative to control point `controlpoint` (default 0). Plane: normal `plane` (default 0 1 0,
  ASSUMED key), the plane at `distance` along it (the preview's -200 is the floor under the system). Sphere: `origin`, `radius` (default
  50, ASSUMED from the preview's picture), hit from outside. Quad (the editor's "collision rectangle"): `origin`, `size` = width along x,
  depth along z (default 100 100), facing +y (the preview's quad is a floor seen edge-on), turned by `angles` in degrees (ASSUMED), hit
  only from the front inside the rectangle. Box: not a WE element anywhere but in the names; ASSUMED an axis-aligned box at `origin` with
  full extents `size` (default 100 100 100), hit from outside. Bounds: the scene's rectangle (0..width, 0..height of the scene, in scene
  units), hit from inside, in x and y; the renderer hands each system its matrices to the scene every frame (`setSceneSpace`).
- **`capvelocity`**: the speed is cut to `maxspeed` (default 100, ASSUMED), inside the blend window.
- **`vortex_v2`**: as `vortex` but the push applies at every distance (inside `distanceinner` the inner speed, beyond `distanceouter` the
  outer one: the presets' 32 unit vortex swirls particles that spawn 256 units out), plus `centerforce` (units/s², towards the axis).
  `flags`: 1 measures the distance from the axis line, else from the centre point; 2 "maintain distance to center": the velocity across
  the circle is removed and the turn is kept on the circle; 4 "ring shape": within `ringpulldistance` of the ring (`ringradius` out,
  `ringwidth` wide) the speed across the ring is steered towards closing the gap at `ringpullforce` (default 5) per second of the gap and
  fades inside the width: each step the speed across moves `min(1, 10 * dt)` of the way to the wanted one (ASSUMED smoothing). ASSUMED: the bit meanings (they match the editor's labels), the pull law and its default. Higher bits are reported (`particle vortex_v2 flags N`).
- **`maintaindistancetocontrolpoint`**: the particle keeps its distance to control point `controlpoint` (default 0): `distance` when given
  (ASSUMED key), else the distance it had when the operator first saw it; the gap closes and the velocity along it fades at
  `variablestrength` (default 5) per second. ASSUMED.
- **`maintaindistancebetweencontrolpoints`**: the particle keeps its place along the line from `controlpointstart` (0) to `controlpointend`
  (1) (ASSUMED keys, those of `mapsequencebetweencontrolpoints`), the place it had when the operator first saw it: it moves with the line
  when the points move and what pushes it along the line is undone; across the line it moves freely (so turbulence still bends a
  lightning bolt). ASSUMED.
- **`reducemovementnearcontrolpoint`**: the velocity decays as v *= exp(-reduction * dt), the reduction `reductioninner` within
  `distanceinner` of control point `controlpoint`, `reductionouter` from `distanceouter` on, by distance in between (defaults 1, 0, 0, 100;
  ASSUMED law and defaults; the presets' 1000 stops a particle at once).
- **`remapvalue` / `remapinitialvalue`** (the old `remapvalue`, velocity and speed from noise, is the special case below): the input
  (scalars above; `size` in the files' units, twice the drawn width; clocks are the system's time, `timeofday` the local day 0..1; a vector
  read as a scalar is its length; `layerorigin` is the system's origin) is brought to 0..1 by `inputrangemin`..`inputrangemax` (0..1),
  through the transform function (`none` clamps; `sine` 0.5 + 0.5 sin(2 pi x s), `square`, `saw`, `triangle` with s =
  `transforminputscale` periods per unit; the noises are value noise, s cells per unit), then onto `outputrangemin`..`outputrangemax`
  (0..1), and assigned to the output, or multiplying it, added or subtracted. A vector input onto a vector output works per component.
  Outputs written: `size` (assigned and added values in the files' units), `opacity`, `color`, `maxlifetime`, `speed`, `velocity`,
  `position`, `rotation` and `angularspeed` (z); the others are reported (`particle remap output X`) and left alone. In the operator,
  multiply and add of size, opacity and colour work on this step's value when an earlier operator rebuilds it (fades, changes,
  oscillators), else on the initial value, so nothing piles up from step to step; for velocity, speed, position and rotation they are rates
  (added per second, multiplied by the factor to the power dt). Without an `input`, a noise function reads the particle's position
  (`transforminputscale` cells per 1000 units, each velocity component its own noise): the rain presets, as before. **Change:** the old
  `remapvalue` ignored `operation`; now an explicit one is honoured in this mode too (the library's rain presets all write "remap", so
  they draw as before). `timeofday` is read once a step. A non-zero `flags` is not read and is reported (`particle remapvalue flags`;
  the rain presets have 3). The absent input and
  output default to `size` (the editor's panel does the same); the absent operation is "remap" (assign). ASSUMED: the mapping, the
  transform shapes and scales, the rate reading in operators.
- **`colorlist`**: one of `colors` (each as likely; 0..1, or 0..255 when a value is above 1) times the instance colour, replacing the colour.
  Without `colors`, with an empty list or with something that is not an array the colour stays as earlier initializers made it and the
  element is reported (`particle colorlist without colors`); a list longer than 256 entries keeps the first 256 and is reported
  (`particle list colors cut to 256`).
- **`hsvcolorrandom` `huesteps`** (in a preview): only that many hues, evenly spread over the hue range.
- **`inheritcontrolpointvelocity`**: adds the velocity of control point `controlpoint` (default 0) times a factor between `min` and `max`
  (default 1). The velocity is how far the point moved between the last two updates over the simulated time between them, in the
  system's space; a pointer-linked point has no velocity until its place is known twice in a row (no jump from its offset to the
  pointer). The preview turns the whole system with a script on its parent, which in our local-space simulation does not move the
  control point (systems with `flags` 1, likely world-space simulation, are not simulated in world space).
- **`positionoffsetrandom`**: adds up to `distance` (default 100) units of three-octave value noise of the place (`scale` per 100 units,
  default 1), the clock (`timescale`, default 1) and the particle's birth number, so the particles of one burst (a lightning bolt laid out
  by `mapsequencebetweencontrolpoints`) lie on a smooth random line that changes with time; flat systems stay flat. ASSUMED.
- **`inheritinitialvaluefromevent` / `inheritvaluefromevent`**: the value is the first text member that is one of the event words (the
  member's name is not known; none is written in any file), else `setcolor` (ASSUMED default). The parent particle's values are those of
  the particle the copy follows (every frame, `eventfollow`) or the particle at its birth / its last frame (`eventspawn` / `eventdeath`).
  At birth multiply and add work on the particle's own initial value; as an operator, multiply works as in remap, and "add" of a motion
  carries the particle along (the parent's velocity moves it, its angular velocity turns it). ASSUMED. In a system that is not an event
  child (no parent particle) both do nothing, silently: whether a file is an event child is known only to its parent.

## Operator audio response

The library carries `audioprocessing*` on two operators only: `vortex` (6 scenes) and `turbulence` (4); no other operator has it. The keys, defaults and level are the emitter's (the section above): the factor `boundsMin + (boundsMax - boundsMin) * pow(level, exponent)` of the selected channel and bands. **Assumed:** it multiplies the operator's strength and nothing else: the vortex's push (`speedinner`/`speedouter`) and the turbulence's acceleration (its drawn speed); the same default bounds "0.8 1.0" and exponent 2 apply when a key is absent (the turbulences of the library give only the mode and often `audioprocessingfrequencyend` 2). A mode above 3 is read as 3 and reported (`particle operator audio mode N`); any other operator with a mode above 0 is not followed and reported (`particle operator audio response`). A vortex or turbulence with a mode makes the engine capture audio (`particleUsesAudio`).

## Sprite sheets on several images

The particle shader lays a sheet's frames out as a grid (`sheetCols` x `sheetRows`) on one image, and a draw binds one image, so a `.tex` sprite sheet that spreads over several images (`Tex::pages`, or `droppedPages`) is drawn from the first image only; the definition reports it as `particle sprite sheet pages` (it reads the texture's header at load time). Sampling the right page would need one draw per page or an array texture; not done (no library particle sheet is known to need it).

## Library survey: flags, wind, gravity

Survey of the 674 workshop items of this machine (492 scenes with a `scene.json`; loose files and `scene.pkg`) plus the WE preset particles in `assets/particles`; script `~/.cache/murasaki-tests/p3b/survey.py`, output `survey.out` there.

- **Renderer `flags`**: only the value 1 occurs (every other renderer has 0 or none): `sprite` 43 renderers in 21 scenes, `rope` 6 in 4, `ropetrail` 1 in 1.
