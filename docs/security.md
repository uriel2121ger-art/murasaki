# Security

Steam Workshop content is not code-reviewed. Malware has reached Steam Workshop before (for example the compromised *Downfall* mod for Slay the Spire in December 2023), and a wallpaper is a program's worth of input: web pages run JavaScript, scenes are parsed by native engines. This page says what Murasaki does about it, what it does not, and how to change the defaults.

## The invariant: items are never executed

Murasaki never runs a file from an item. Wallpaper Engine items of type `application` are listed but never started, and no importer, preview or metadata step launches anything the item ships. A new feature that wants to run an item's file would be a security change and has to be reviewed as one.

Items that ship programs are still *flagged*, because the same Workshop folder may be used by other software:

- At index time each importer scans the item folder (at most 6 directories deep, 2000 files, 20 findings; symbolic links are not followed). Scene `.pkg` packages are read through their file table (at most 20000 entries) and their entries judged the same way; a finding reads `scene.pkg:inner/path`. A file is flagged when its content is an ELF, PE (`MZ` with a `PE\0\0` header) or Mach-O executable, when it starts with `#!` (a script, except in web files), or when its name ends in `.exe .dll .scr .bat .cmd .ps1 .vbs .sh .AppImage .jar .msi .lnk`. JavaScript is never flagged: web wallpapers are made of it. A `project.json` of type `application` is flagged too.
- The item JSON carries `risks: [{kind: "executable"|"application", file}]`. The library shows a warning badge on the card, and the item page a warning that lists the files. Nothing else changes: the item still works.

## Layers

### 1. Web wallpapers have no network by default

A web wallpaper can reach the internet only if you allow it for that item (switch "This wallpaper can use the internet" on its page; the library shows a globe on such items). The permission is stored in `$XDG_CONFIG_HOME/murasaki/permissions.json` and set with the D-Bus call `SetItemPermission(itemId, "network", allowed)` (`murasakid` API revision 8). Allowed pages can also track you or use your computer to mine: enable it only for wallpapers you trust.

What stays possible without the permission: everything local. The page's own files (`murasaki-item:` URLs), `data:` and `blob:` URLs, and `file://` inside the item's own folders (and files you picked for its properties).

How it is enforced, outermost first (`src/render`):

| Layer | What it does |
|---|---|
| **One profile per shown wallpaper** (`webprofilefactory.cpp`) | Every shown web wallpaper gets an off-the-record web profile of its own: a separate network context with no cookies, cache, authentication cache, sockets or connection hints shared with any other wallpaper. Each profile has its own scheme handler and request interceptor, which know whether that wallpaper has the permission. A profile is deleted shortly after its wallpaper leaves the screen. |
| **Network gate** (`networkgate.cpp`) | The web engine is started with all its traffic sent through a forwarding proxy that lives in `murasaki-surface` and listens on 127.0.0.1 only; it also gets no UDP for WebRTC and no implicit exemption for loopback. The proxy serves only requests that carry a valid token (HTTP Basic credentials in `Proxy-Authorization`, checked for every connection). A token is a random 128-bit value issued to the profile of one wallpaper that has the permission, and only that profile answers the proxy's challenge with it; every other profile gets a 407 for everything it does on its own (preconnect and DNS hints, WebRTC's TCP sockets, ...). Revoking a token (the wallpaper left the screen, or the permission was turned off) drops the connections made with it. With no token issued the proxy refuses everything. The gate resolves the target itself and connects to the address it checked (no second lookup, so no DNS rebinding); it refuses loopback, private (RFC 1918), shared (100.64.0.0/10), link-local, unique-local, multicast and reserved addresses, also when hidden in IPv6, so a page cannot reach the machine or your network through it. Each token holds at most 128 connections and idle ones are dropped after two minutes. If the gate cannot listen, it fails closed: no token is issued, the engine's proxy points at a port nobody serves and web wallpapers have no network at all. |
| **Request interceptor** (`fileaccessinterceptor.cpp`) | Every request the profile makes is checked. Anything that is not the item scheme, `data:`, `blob:`, `about:` or a `file://` inside the item's folders is blocked unless the profile belongs to a wallpaper with the permission. This covers fetch, XHR, images, scripts, styles, frames, beacons, navigations and WebSocket handshakes. |
| **Content-Security-Policy** (`itemschemehandler.cpp`) | Pages without the permission are served with `connect-src murasaki-item: data: blob: file:`, which also governs workers and WebTransport. |
| **No WebRTC / WebTransport in the page** (`WebItem.qml`) | Without the permission `RTCPeerConnection`, `WebTransport` and related classes do not exist in the page. |

The layers are independent: the tests (`tst_webnetwork`) show that a page with the permission but without the gate's credentials gets nothing out, and that a hostile page without the permission shown **at the same time** as an allowed one gets nothing out (its fetch, WebSocket, WebRTC over TURN/TCP in an `about:blank` frame and preconnect hints all fail) while the allowed page's requests succeed.

Costs and limits, so you can judge them:

- Memory: each shown web wallpaper has its own renderer process, about 120 MiB more per additional web wallpaper (measured with the probe page of the tests).
- With the permission, WebRTC works over TCP only (no UDP, hence no direct peer-to-peer media), and the first page load takes one extra request to the gate to introduce the credentials.
- The gate is a local proxy: other programs of your user could use it as one if they had a token, which they never see.

Not covered: video wallpapers (decoded by mpv inside `murasaki-surface`) and the page's own CPU use.

### 2. Scene engines run in a sandbox: a mount namespace, then Landlock

Scenes are parsed and drawn by a native engine (`murasaki-scene-vk`) from untrusted data. `murasaki-surface` starts it behind `murasaki-sandbox`, a small helper without Qt (`src/sandbox`). The same applies to `murasaki-scene-vk --check`, which parses the item to decide whether the engine can draw it. The helper works in two layers:

1. **Mount namespace (bubblewrap), when `bwrap` is installed and works.** The engine runs in new network, process and IPC namespaces (`--unshare-net --unshare-pid --unshare-ipc --die-with-parent --new-session`, capabilities dropped, environment cleared except locale, paths and the graphics, audio and Murasaki variables). It sees only: the files of the policy below, `/dev/dri/renderD*` (render nodes only, no display control), a fresh `/proc`, and a **private runtime directory that holds nothing but the PipeWire socket and the PulseAudio directory**. There is no session bus socket and no Wayland socket in it, which closes the hole Landlock alone has (see below). Without network namespace support or when bwrap fails its probe, the helper says so once and goes on with Landlock only.
2. **Landlock** (kernel 5.13+; the helper uses the best ABI the kernel offers), applied inside the namespace, or alone: it sets `PR_SET_NO_NEW_PRIVS` and builds the ruleset below. The bridge socket to `murasaki-surface` is a descriptor the engine inherits and keeps working in both layers.

The policy (the *scene profile*, `src/sandbox/profile.cpp`):

| Access | Paths |
|---|---|
| read and execute | the item, Wallpaper Engine's `assets`, the engine's own file, its folder (unless it is a `bin` directory) and the library directories its ELF header lists, `~/.local/lib/murasaki`, `/usr`, `/lib*`, `/bin`, `/sbin`, the loader's configuration, `/etc/fonts` and the fontconfig caches and user fonts (`/var/cache/fontconfig`, `$XDG_CONFIG_HOME/fontconfig`, `$XDG_CACHE_HOME/fontconfig`, `~/.fonts`, `~/.local/share/fonts`), `/etc/localtime` and `/etc/timezone` (a clock scene shows local time), `/etc/vulkan`, `/etc/glvnd`, `/etc/drirc`, PipeWire, PulseAudio and ALSA configuration, `/sys/devices`, `/sys/dev`, `/sys/class/drm`, `/sys/bus/pci`, `/proc/self`, a few `/proc` files, `$XDG_RUNTIME_DIR/pulse` |
| read and write | `/dev/dri`, `/dev/nvidia*`, `/dev/null`, `/dev/zero`, `/dev/urandom`, `/dev/random`, `/proc/self/task` (thread names), `$XDG_CACHE_HOME/murasaki/shader-cache` and `.../gpu-cache` (the GPU drivers are pointed there with `MESA_SHADER_CACHE_DIR` and `__GL_SHADER_DISK_CACHE_PATH`) |
| TCP | bind and connect refused (Landlock ABI 4 and newer; the network namespace has no network at all) |
| scopes | abstract unix sockets and signals to processes outside the sandbox refused (ABI 6 and newer) |

Everything else is refused, so a compromised engine cannot read your home directory (`~/.ssh`, browser profiles, ...), write outside the caches, or reach the network or your session bus. Audio works: the PipeWire and PulseAudio sockets are in the private runtime directory, and the engine reads their configuration. Without the mount namespace, Landlock before ABI 9 cannot restrict connecting to a pathname unix socket, so a compromised engine could still talk to services that listen on one, such as your session D-Bus; this is why the namespace matters and why Settings shows whether it is in force.

Unusual locations. An item library or the assets directory on another disk, in Flatpak Steam (`~/.var/app/com.valvesoftware.Steam/...`) or in SteamCMD's content root is mounted at its own path, as any other. A library path that is itself a symlink is mounted both as the link and at what it points to (a link to another disk used to dangle inside the namespace). A path that merely starts with `/proc` (`/procurement/...`) is a normal path; only `/proc` itself is procfs. A PipeWire socket named by `PIPEWIRE_REMOTE=name` is bound next to `pipewire-0`; an absolute `PIPEWIRE_REMOTE` is not.

Left out on purpose: `/etc/machine-id` (a stable identifier of the machine that nothing a scene does needs; PipeWire clients create their node without it), `/etc/hosts` and `/etc/resolv.conf` (no network), `/run/dbus` and `$XDG_RUNTIME_DIR/bus` (the session bus), the Wayland socket.

Limits: the two shader cache directories are shared by all scenes, so a compromised engine could plant a bad cache entry that another scene would load (the caches are keyed by content, which makes this hard but not impossible); per-scene cache directories would cost the sharing that makes launches fast.

**What is in force.** Settings, Advanced shows what this system offers ("Landlock ABI 8, TCP refused, mount namespace yes", from `murasaki-sandbox --report`), and the surface logs it at each scene start. By default an engine that cannot be confined (no helper installed, no Landlock) still runs, as it always did, and the helper says so once in its log. Turn on **"Do not start a scene engine that would run without the sandbox"** (setting `requireSandbox`) to refuse instead: the scene is not shown and the reason is reported. Refusal covers a missing helper, a kernel without Landlock, and a system where TCP can be refused neither by Landlock (ABI < 4) nor by a network namespace.

**Media covers and what plays.** The sandboxed Vulkan engine has no session bus and no network, so a scene that shows the cover of the playing media (`$mediaThumbnail`) or listens to the media events of SceneScript gets them from the surface: the surface reads the MPRIS players, decodes the picture (on a worker thread, plain raster formats only, size checked from the header, at most 512 x 512 sent) and passes the pixels over the bridge socket as a sealed memfd. Only scenes that use the media are told anything (the engine says so after loading its scene), and the players are not read while none does. What a scene is told is the title, artist, album, album artist, genres, position and the cover of the player it follows: **a Workshop script can keep that in its own storage (`localStorage`, in the item's data directory) and write it in its log (`console.log`), where the surface's log files hold it.** Turn the whole thing off with the setting `mediaShare` (Settings, Advanced, "Media"): nothing is read and such scenes are told that nothing plays. An `https://` cover is downloaded by the surface, directly (no proxy), only from public addresses (checked on the resolved addresses; a DNS name that answers differently at connection time is the accepted residual risk, since the address comes from a local player), at most 8 MiB and 15 s each; turn it off with the setting `mediaRemoteArt` ("Media cover"): only `file://` covers are read then. A picture file named by a player can be any picture the user can read. Both settings count as off until the surface has read them from the daemon. The `MediaWants` message by which a scene says it uses the media is a courtesy of the engine, not a barrier: an engine that lied (or one running a hostile scene) is told what plays like any other that asks, and the one real barrier is the setting `mediaShare`. The host applies a scene's change of mind at most once a second. Details: docs/scene-vk/formats.md, "Media cover".

**Shortcuts of a wallpaper (applications).** Dock-style wallpapers have slots (`usershortcut` properties) the user fills with an application; the wallpaper shows its icon and a click starts it. The scene is untrusted and gets only this: its script can call `engine.openUserShortcut(name)` with the key of a property, nothing else. It never learns which application it is (the engine is told only the application's display name, at most 64 bytes with control and direction characters removed, and its icon, 256 x 256 pixels as a sealed memfd). A request becomes a started program only if **all** of this holds: the setting `shortcutsLaunch` is on (default on); the key is a `usershortcut` property of that wallpaper's own `project.json`, read by the host, and the user stored an application for it; the surface itself saw a real button press on the wallpaper within the last 0.75 seconds (one press, one launch: a script cannot make one) and the wallpaper is shown; at most one launch per 2 s for the wallpaper, 6 a minute over all of them and not the same application twice within 5 s. The click and visibility checks are the surface's (only it sees the pointer events and what is shown; the daemon cannot see them) and the daemon trusts the session bus for them: `LaunchShortcut` is a method of the daemon's D-Bus interface, so any process of the user can call it, and such a process could start the application itself; what the daemon adds is the user's switch, the global rate limits and that the application is the one the user stored. The engine cannot call it: the sandbox gives the scene engine no session bus (`murasaki-sandbox` with bubblewrap mounts a runtime directory that holds only the audio sockets and has no network namespace, so neither the bus socket nor an abstract socket is reachable; without the sandbox, because the user turned it off or it is unavailable, the engine runs with the user's own rights and needs no one to start a program for it), and its only channel is the bridge socket, whose `ShortcutLaunch` the surface validates. The surface does not start programs: it passes the request to the daemon (`LaunchShortcut(output, desktop, item, key)`), which reads the stored application from the one assignment that `ResolveAssignment(output, desktop)` returns, and not from any other (a wildcard assignment, another desktop's), resolves it against the installed desktop entries and starts it with `gio launch <file>` (else `gtk-launch <id>`, else the entry's own `Exec` line with its field codes dropped, never through a shell; an entry that needs a terminal or has an `Exec` that cannot be read safely is not started). No text of the scene reaches a command line, a path or the environment. The `.desktop` files and the icon files are untrusted input of the host: size, count and every string are bounded; an icon path must resolve inside an icon directory and decodes within 4096 pixels a side and 16 Mpixel (only png, jpeg, webp and gif; a theme icon is found by looking at the theme's files and may be an SVG, which QtSvg draws when the build has it). Icons are decoded, and theme SVGs parsed, in the surface process (the host), on a worker thread of its own, one icon at a time, and an icon that takes more than a second is dropped (the slot keeps the scene's default); the files are the user's own theme and application directories. Residual risk: a script can ask once per click for any of the applications the user assigned in that wallpaper, and the user may not remember that a click on a dock icon starts an application; a malicious `.desktop` in the user's own applications directories is outside this model (the user can already start it). Details: docs/design/specs/2026-10-21-user-shortcuts-design.md.

Turn the sandbox off, only to find out whether it breaks something: **Settings, Advanced, "Run scene engines in a sandbox"** (setting `sandboxEngines`). Scenes on screen start again. If a scene works only with the sandbox off, please report the missing path: run `murasaki-sandbox --bwrap none --profile scene --item DIR -- strace -f -Z -e trace=%file ENGINE ...` and look for `EACCES`.

Install: `cmake --install` puts `murasaki-sandbox` next to `murasaki-surface` and the scene engine. `$MURASAKI_SANDBOX` overrides the lookup. `bwrap` comes from your distribution (`bubblewrap`); on Ubuntu with restricted user namespaces its AppArmor profile allows it.

Check it on your library: `python3 tools/compat/run.py --engine vk --sandbox` renders every installed scene behind the helper and must report the same results as without `--sandbox` (see `tools/compat/README.md`).

### Importing pets

Importing a pet (docs/pets/import.md) parses files the user picked, and an Anima package or archive can be hostile, so the work is not done in the daemon: `murasaki-petimport` runs behind `murasaki-sandbox --profile import` (a mount namespace with no runtime directory, so no session bus or display socket; read the system and the named sources, write the job's output folder, no TCP, a cleared environment, limits, dies with the daemon; required by default: `importRequireSandbox`, which also means imports are refused on a system that forbids unprivileged user namespaces) and limits itself (4 GiB of address space, 60 minutes of CPU (the threads of a decoder add up; the job's own 15-minute time budget ends it first), nice 19; the daemon adds 30 minutes of wall time, one job at a time). Every limit is checked from headers before anything is allocated; the image format is decided from the first bytes and handed to Qt as the format, so no other image plugin ever parses a hostile file; a ZIP is read by a bounded reader (end record exactly at the end, no ZIP64 or several disks, no encryption, no symbolic links, names never used as paths, ratio and inflated-size caps, CRC verified) and nothing from an archive is written under its own name; `core.exe` and every other program in a package are never extracted or run (`core.exe` is only hashed). `actions.mddo` is read by a strict parser that never evaluates anything. The animations inside an `.mdaa` are copied after the header readers accept them and are decoded later by the pets' own decoder, like any Workshop animation. `requireSandbox` makes a job fail with `sandbox unavailable` instead of running unconfined. `tools/compat/pets_import_sweep.py` runs a synthetic corpus of good and hostile inputs through the helper and checks the output with Pillow.

### Session facts (which window is fullscreen)

`murasaki-surface` publishes what the window monitor of the session says (docs/pets/session-facts.md) on the session bus. The names of the applications that are open, the focused one and
the game/battery facts are **private to Murasaki**: only the owners of the daemon's and the overlay's bus names get them; every other process gets only which outputs have a fullscreen or
covering window. The facts are never stored or logged beyond one line naming the monitor, and they carry class names only (no titles, no window contents). The change signal has no argument.

### Not sandboxed yet

Web and video wallpapers live inside `murasaki-surface`, which needs D-Bus, Wayland and portals, so they are not under Landlock; the web layers above are what protects them. Future work: move the web and video renderers into their own sandboxed helper processes.

## Puppets: a model is hostile input drawn on the GPU

A puppet (`docs/pets/puppets.md`) is a folder the user adds: an Inochi2D `.inp` and nothing else is shown by this build. Its bytes are untrusted, and they are parsed and drawn by `murasaki-puppet --engine`, a process of its own (no Qt, no script engine,
no audio, no video) that neither the daemon, nor the overlay, nor the GUI ever links.

- **Before anything is drawn** `murasaki-puppet --check` (also run by the daemon, task 8) validates the folder: no link of any kind in it, paths named by a manifest that stay inside it, every count and size under the limits table of `src/core/puppetlimits.h` (one table,
  pinned to the document by a test), strict JSON (no repeated key, bounded depth, values and strings), well-formed UTF-8, magnitudes under `kMaxCoordinate`, mesh indices inside their vertices. A puppet that breaks a rule is refused whole, not repaired.
  Every file of an item is opened with `openat2` (`RESOLVE_BENEATH | RESOLVE_NO_SYMLINKS | RESOLVE_NO_MAGICLINKS`; a per-component `O_NOFOLLOW` walk where it is missing), never by a concatenated path.
- **The engine runs behind `murasaki-sandbox --profile puppet`** (a mount namespace, then Landlock; refused when it cannot be set up if `requireSandbox`): it reads the model folder and the system, writes only the GPU render nodes (`/dev/dri/renderD*`, never a card node) and its own two shader caches
  (`puppet-shader-cache`, `puppet-gpu-cache`: not the scene engines', so a model can not plant what a scene reads later), has no home,
  fonts, audio, session bus, display socket or TCP, no core dumps, and is killed with its parent. A seccomp denylist (hand-written BPF, no library) makes `io_uring_*`, `bpf`, `userfaultfd`, `perf_event_open`,
  `ptrace`, `process_vm_*`, `keyctl`, `open_by_handle_at`, `mount` and the new mount API, module loading, `pidfd_getfd`, `kcmp`, `unshare`, `setns` and `kexec_*` fail with EPERM; `clone` with any `CLONE_NEW*` flag fails with EPERM (otherwise a nested user namespace would give
  back every capability inside it) and `clone3` answers ENOSYS so that glibc falls back to `clone`; other ABIs (32 bit, x32) are refused whole. `ioctl` is not filtered (the drivers use it all day). The filter fails closed only with `--require`, which the host passes when `requireSandbox` is on (the default);
  without it a filter that cannot be installed is a warning and the engine runs unfiltered.
  **The display's KMS nodes** (`/dev/dri/card*`) are kept out three ways: under the mount namespace they do not exist; the profile gives write only to `renderD*`; and with Landlock ABI 5 or later (kernel 6.10) a file opened under the directory's read right has no `IOCTL_DEV` right, so a KMS ioctl on it is EACCES. It is that ioctl right, not the missing write permission, that stops a KMS query (the DRM ioctls do not check the open mode). On an older kernel without the mount namespace, a card node can be opened read only and queried; the profile cannot prevent it. Its only channel is the bridge socket it inherits. The optional Cubism Core library the user installs would be the one extra read-only path.
- **Bounded work.** The mesh group grid, the number of fixed physics steps per update, the motion queue, the texture pixels and the picture's long side are all capped (CPU and memory). The GPU is bounded too, but only per frame and by estimate:
  before a frame is recorded the engine works out on the CPU the area its triangles cover once clipped to the picture, mask sources drawn again for each use and group images included. A frame over `kMaxOverdrawFactor` (64) pictures, or that would
  write more than `kMaxPositionVertices` vertex positions, is not drawn; `kMaxHeavyFrames` (30) such frames in a row end the engine with the "model refused" status (`puppet: too heavy`), and so do `kMaxSlowFrames` (3) frames in a row whose GPU work took
  over `kMaxSlowFrameMs` (250 ms). What this does not do: stop a single frame under the estimate that is slow on a weak GPU (the time watch ends the model after the third), or bound the CPU cost of the estimate itself, which is linear in the triangles
  (the footprint sent to the overlay is limited to `kMaxHitMaskWork` units of work per frame and is not worked out again when nothing that shows has changed). An engine that is paused does not draw; the process has no timers when no puppet is shown.
- **A crash is contained.** The overlay restarts a crashed engine and blocks a model that crashes it three times (the crash ledger, across restarts); a refusal, no GPU or no sandbox is not retried.
- **What the engine tells the overlay** is pictures and a coarse mask of where the puppet is (a bit grid), nothing else; what the overlay tells it are sizes, a pause flag, a frame rate, the pointer position and the JSON commands of `PuppetSession` (which names only parameters of the model).

- **Settings of puppets.** `puppetMaxPixels` is clamped to 1 to 16 megapixels. `puppetCorePath` is only stored: `SetSettings` refuses a path that is not an absolute plain file owned by the user and not writable by group or others, and nothing in this build opens or loads it (no `dlopen`).
- **A stopped engine is retired, not waited for.** The overlay kills a stopped or lost engine on a timer without blocking, and starts the next one only after the old one has gone: never two engines alive.

## Screen matching: the helper that sees the screen

Screen triggers compare regions of the screen with reference pictures. The pixels of the screen are the most sensitive thing Murasaki can ever read, so they are read by one small process, `murasaki-screenmatch`, and
by nothing else; the daemon never maps a frame.

- **What it holds.** Two inherited descriptors and nothing more: the PipeWire remote the daemon opened through the portal (`OpenPipeWireRemote`, after the user said yes to the desktop's dialog) and one socketpair to the daemon. It has no option that names a file, a path or a frame source (a test pins this); the fake source of the tests is an in-process interface.
- **The sandbox** is `murasaki-sandbox --profile screenmatch` (a mount namespace when bubblewrap works, then Landlock; refused when it cannot be set up if `requireSandbox`). It reads the system's libraries and PipeWire's own configuration and plugins, the helper's own file and the libraries its RUNPATH names, and nothing else (not the directory the helper sits in, and none of the scene engine's extra paths): no home, no runtime directory, no GPU, no fonts. It writes nothing, anywhere (`RLIMIT_FSIZE` is not
  used, Landlock has no writable path), has no TCP, no core dump and 256 descriptors, and dies with its parent. The helper also protects itself before anything of the screen is in memory (`PR_SET_DUMPABLE` 0 and `RLIMIT_CORE` 0, so a run without the wrapper leaves no dump either and a process of the same user cannot ptrace it), checks that its two descriptors are sockets and closes every other one (`--selftest` prints the core limit and the dumpable flag; a test asserts both). As its first act the helper loads a seccomp filter (the puppet list, plus `socket`, `connect`, `bind`, `listen`, `accept`, `accept4`, `execve` and `execveat`): it can neither open a connection nor start a program, so the two descriptors are all it can ever talk to. The filter is loaded by the helper
  and not by the wrapper because it refuses the exec that started it; `socketpair`, `sendmsg` and `recvmsg` stay, since PipeWire passes buffer descriptors over its socket. A test runs the helper behind the real wrapper and checks each refusal by its errno (and the same under and without the mount namespace).
- **Frames.** Only the newest frame of a stream is ever looked at: older buffers go back to the server unread. Buffers are shared memory (memfd or pointer): the helper asks the server for nothing else and refuses a dma-buf that a server hands over anyway. `--buffers any` (never passed by default; **experimental**) lets a dma-buf be mapped and read as a linear buffer: it does not offer a modifier and does not synchronise with the GPU (`DMA_BUF_IOCTL_SYNC`), so a tiled buffer reads as garbage, never as a crash. Every read is bounded by the chunk the server declared and by the mapping, judged in one pure function (`src/screenmatch/bufferguard.cpp`, `tst_screenmatchbuffer`: offset and size inside the mapping without a wrap, a stride that covers a row and a chunk that covers the last row, the corrupted flag, a failed mapping, the format of the moment); the size is checked at 16384 per side, and the pixel cap (134 million) is applied to each crop by the matching core. A server that truncates the memory behind a buffer can still make the helper fault (SIGBUS), which is a counted crash: it costs the feature, not the data; a crop is
  prepared straight from the buffer by `prepareScreenPictureFromPixels` with `screenRowStepFor` (no full-size copy, no 360 pixel intermediate).
- **What leaves.** Lines of at most 4096 bytes (`src/screenmatch/protocol.h`): scores in permille per region, `t` and `state` lines, `ok` and `err`. Nothing of the live screen is in any other line. The one exception is the explicit capture the editor asks for ("Capture now"): one rectangle, scaled to a longer side of at most 360 and sent as RGB in chunks, only when the helper was started with
  `--allow-capture`, at most one a second, and shown to the user for confirmation before it is stored.
- **What comes in.** The daemon's commands are parsed by a strict grammar: printable ASCII, single spaces, counts and numbers in range, one spelling per value (a reference travels as the 1024 bytes of its 32x32 grey grid in canonical base64). A refused line is answered with a fixed reason that never echoes it; a line over 4096 bytes is dropped to its newline and counted, in bounded memory.
  At most 4 triggers, 8 regions each and 16 in all, 64 steps a region and 64 pet rectangles.
- **A crash is contained.** The host (`ScreenMatchHost`) counts a crash in the crash ledger (keyed by the helper's binary) and, after the third, turns screen matching off until the user turns it on again. The PipeWire remote of a dead helper cannot serve another, so there is no automatic restart: whoever owns the portal session opens a new remote. The desktop ending the share, a build without PipeWire and
  the sandbox's own refusals are not crashes.

### Screen triggers: what is read, where it goes, what is kept

| What | Who reads it | Where it goes | What is kept, and for how long |
|---|---|---|---|
| The pixels of the shared screens | Only `murasaki-screenmatch`, through the PipeWire remote the portal gave (after the desktop's dialog) | Nowhere: each tick the helper crops the regions, turns them grey, shrinks them and scores them; a frame is held only until a newer one replaces it | Nothing on disk. In the helper's memory only the newest frame; no core dump (`RLIMIT_CORE` 0, not dumpable) |
| The scores (permille per region) | The daemon | The trigger engine; `TriggerState` (`screen.score`), `ScreenWatchState` and `ScreenWatchChanged` carry numbers on the session bus, which every client of that bus can read | In memory only, until the next tick. A score tells how much a region looks like its reference, not what it shows (a residual of the session bus's trust model: a process of the same user can ask whether a picture is on screen, not what is) |
| The references of a trigger | The daemon (decodes them under a cap into a 32x32 grey grid) | To the helper, as 1024 bytes a region step | PNGs scaled to at most 360 pixels in `$XDG_DATA_HOME/murasaki/triggers/<trigger id>/`, deleted with the trigger; imported ones are only the frames the pack uses |
| The explicit capture ("Capture now") | The helper takes one rectangle of one region, at most one a second, only while the user is watching and the session is unlocked | Helper -> daemon over the socketpair (RGB, at most 360 x 360) -> a PNG in the daemon's memory (a page-aligned mapping excluded from core dumps and zeroed on release) -> a **unicast** signal `ScreenCaptured` to the bus name that asked (never a broadcast), whose editor shows it | Held in memory for at most 60 seconds, one at a time; dropped when the watch stops, the session locks, the share or the helper fails, or the user discards it. Only if the user keeps it does it become a reference on disk; only the bus name that asked may keep it |
| The portal's restore token | The daemon | Back to the portal at the next Start | Only with the setting `screenRemember`, in `$XDG_STATE_HOME/murasaki/screen-state.json` with mode 0600, single use (cleared when sent, kept only as announced), wiped when the setting goes off |
| The helper's output besides the protocol | The daemon forwards the helper's stderr to its own | The journal | Fixed strings and PipeWire's own warnings (node names, formats); never pixels, scores or paths. The daemon logs none of a capture, a score or a reference |

**Review (task 7): no live pixel leaves the helper except the explicit capture.** Every path was traced from the PipeWire buffer to the bus:

1. *Into the helper.* `acquire()` (`src/screenmatch/pwsource.cpp`) validates the chunk the server declared (`bufferguard.cpp`: offsets inside the mapping without a wrap, a stride that covers a row, the last row inside the chunk, no corrupted flag, no dma-buf unless asked) and hands the session a read-only view. Nothing copies the frame; `prepareScreenPictureFromPixels` reads the crop's rows and keeps a 32x32 grey grid and an 8x8 hash.
2. *Out of the helper.* The helper writes to two places only: the socketpair and stderr. On the socketpair `src/screenmatch/protocol.cpp` formats exactly these replies: `hello`, `ok`, `err` (a fixed reason), `s` (scores), `t`, `state`, `pong` and, for a capture, `shot`/`chunk`/`shotend`. No reply type carries a frame, a grid or a hash; `chunk` is emitted only by the capture path (`session.cpp`), which needs `--allow-capture`, the request id the daemon chose and the one-a-second gap. On stderr the helper prints fixed usage and sandbox messages and PipeWire's own log. The helper opens no file (Landlock without a path), no socket (seccomp) and starts no program, so there is no other way out.
3. *Into the daemon.* `ScreenMatchHost` parses replies with the same grammar (a bad line is counted, never logged). `ScreenWatch::onReply` uses a `Shot`/`Chunk` only while a capture job waits for exactly that request id, bounded by `kMaxCaptureBytes`; otherwise the line is dropped. Scores become numbers fed to the matcher.
4. *Out of the daemon.* Scores and states leave on the session bus as numbers and words. A capture leaves as a PNG in a unicast signal to the requesting bus name; `grep` finds no `qDebug`/`qWarning`/`qInfo` in `screenwatch.cpp`, `screenmatchhost.cpp` or `screencastportal.cpp` that prints a payload. Nothing is written to disk but a capture the user keeps.
5. *Residuals, said plainly.* (a) The scores are readable by every client of the session bus (a number per region). (b) The daemon as a whole is not hardened against core dumps (it is not made non-dumpable), but the held capture is contained: the PNGs of a pending capture (up to 60 s) are kept in `SecureBytes` (`src/core/securebytes.h`), a page-aligned anonymous mapping of their own marked `MADV_DONTDUMP` (and `MADV_WIPEONFORK`), overwritten with zeroes before it is unmapped when the capture is kept, discarded, expires, the watch stops, the session locks or the daemon exits (`tst_securebytes`, `tst_screenwatch`: the mapping carries the `dd` flag in `/proc/self/smaps`, and every buffer is all zeroes when it is given back). The raw RGB picture is overwritten as soon as the PNG is made, and the copies that are made while a capture is produced and sent (the base64 text and the JSON of the signal, and the buffers inside libdbus and Qt) are ordinary heap for a few milliseconds: a dump taken in that instant could hold the picture; one taken at any other moment holds none of it. (c) A same-user process can call `StartScreenWatch` and `CaptureScreenReference` once the user has set `screenTriggersEnabled` and a trigger exists; with `screenRemember` on no dialog is shown again. The brief answer to (c) is the bus's trust model (every client can already call the daemon); the mitigations are that a capture only exists while the user is watching, goes only to its requester and expires.

## Desktop pets: the pointer and the masks

What the pointer features of the pets (hide under the cursor, focus fade, smart dodge, dragging; `docs/pets/behaviours.md`) add to the surface of the program:

- **The cursor position** reaches the overlay only while a pet needs it, and stays in the overlay (it is used to decide whether a pet fades or steps; it is never stored,
  logged or sent anywhere). On Plasma a small script is loaded into KWin over `org.kde.kwin.Scripting`; it reports `workspace.cursorPos` and nothing else (no windows, no
  keys, no files, no network) to the overlay's own D-Bus object `/io/github/uriel2121ger_art/Murasaki/Overlay/Pointer` (`ReportPointer(i, i)`). The object accepts the call only from
  the current owner of `org.kde.KWin` (the owner is followed with a watcher; any other process of your user gets nothing), ignores coordinates beyond +-1,000,000, and does
  nothing while no pet needs the cursor. The script never outlives the overlay: the overlay removes a stale one when it starts, removes its own when it exits, and the script stops
  by itself when the overlay's bus name has no owner. Nothing is loaded into KWin and nothing is exported on the bus for the default setup (pets that are click-through with no behaviour).
- **On Hyprland** the overlay asks the request socket of the instance (`j/cursorpos`), only for sockets owned by your user; **on X11** it reads the pointer the way any X11 client can.
- **The mask cache**: for a pet that plays through the video path the overlay decodes the pet's file once and keeps only a bit grid of where it is opaque, in
  `$XDG_CACHE_HOME/murasaki/pets/<item>-<hash>/<variant>-<hash>-<key>.mask` (a few KiB). Names are made safe path components and hashed, the key follows the file's path, size
  and modification time, and the parser reads nothing it has not bounded first (version, sizes, exact length, a checksum, masks that must nest): a damaged, truncated or hostile
  file is refused and made again. Files are written atomically. Only pets that have a use for masks get one.
- **Input regions** are cut to the opaque pixels of a pet only for pets that take the pointer; a click-through pet never takes input.

### Pet audio: the decode and the player

The sound of a desktop pet comes from a file the user picks, so it is read as untrusted (docs/pets/audio.md).

* **The decode happens once, outside the daemon and the overlay.** `murasakid` runs `murasaki-petaudio --import SOURCE ASSETS` behind `murasaki-sandbox --profile import` (the profile of the pet
  imports: the system, the helper and the one file to read, the sounds folder to write, no TCP, no runtime directory so no session socket is reachable; the
  setting `importRequireSandbox` refuses to run without it). The helper opens only the `file` protocol, takes containers and software decoders from lists by codec id, reads one
  audio stream (every other stream gets no codec before probing, so no video, subtitle or picture decoder opens), checks its limits against what it decodes
  (10 minutes, 8 channels, 128 MiB of output, 1,000,000 packets, a few damaged packets), and stops at a deadline of 5 minutes or on cancel through libavformat's
  interrupt callback. It writes a WAV of one fixed format (`.part`, then rename) named by the SHA-256 of the source. Tests cover renamed text and playlist
  files, a `concat` list, devices, truncation, a memory ceiling (`RLIMIT_AS`) and every accepted format.
* **Nothing else decodes audio.** The overlay links no codec. The player process, `murasaki-petaudio`, maps assets by id (64 lowercase hex characters, so an id can
  not name another place) after a strict check of the 44-byte header against the file's size, and takes a line protocol on stdin: lines of at most 256 printable
  characters, parsed exactly; anything else ends the player. A fuzz test feeds it garbage. The player runs inside `murasaki-sandbox` with the generic policy (read: `/usr`, `/lib`, `/lib64`, `/etc`, the helper and the sounds folder; no TCP) and, like the import,
  follows the setting `importRequireSandbox` (default on): with it the player does not run at all without the helper, a failure of the helper never starts it
  unconfined, and `MURASAKI_PETAUDIO_SANDBOX=0` is ignored. Without it (the setting off), a helper that cannot run the player (status 125 to 127) lets the next start
  run unconfined once, with a warning, and the one after is confined again (the player's own status 3, no audio system, never changes that). **This policy is weaker than the import
  profile and says so: it does not hide the session bus or the runtime directory (the player has to reach the PipeWire socket there; Landlock does not govern
  `connect()` to a Unix socket, and `/etc` is readable), so what the confinement buys is no TCP, no writes, and reads only where listed. It is tested against a real PipeWire;
  what it reads is limited to files this code wrote and checked.
* **The cost of an unused feature is zero**: no process, no audio stream, no thread until a pet with a sound has to make one.
